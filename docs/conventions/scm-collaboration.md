# [컨벤션] 형상 관리 & 협업

> **범위**: 형상 관리 호스팅·레포 구조·브랜치·커밋·이슈 트래킹.
> **변경 시**: 이 문서를 단일 출처로 갱신합니다 ([AGENT_GUIDE 문서 동기화](../AGENT_GUIDE.md#문서-동기화-필수) 참고).

## 결정 사항

| 항목 | 결정 | 비고 |
|------|------|------|
| 형상 관리 호스팅 | GitHub | |
| 레포 구조 | 멀티모듈 모노레포 (Gradle, `*_service` 모듈별 분리) | |
| 브랜치 전략 | `main`(보호, 릴리즈) + `develop`(비보호, 직접 작업) | 1인 프로젝트라 평소엔 `develop`에 바로 커밋·푸시. 별도 기능 브랜치·PR은 선택사항 |
| 브랜치 네이밍 | `type/설명` | 이슈 번호는 더 이상 필수가 아님(붙여도 됨) |
| 커밋 메시지 컨벤션 | Conventional Commits (feat:, fix: 등) | |
| `main` 승격 방식 | 필요할 때 `develop` → `main` 병합 | 매 커밋마다 강제되는 절차는 아님 |
| 이슈 트래킹 / 작업 관리 | 사용 안 함 (필요 시 GitHub Issues 선택적으로) | |

## 규칙 / 적용

### 🌿 브랜치 전략 및 성격

- **`main` 브랜치**: 릴리즈 코드를 담는 유일한 보호 브랜치입니다. 직접 커밋·푸시가 금지되며, 이는 `.claude/hooks/` 검사와 git pre-push 훅으로 강제됩니다.
- **`develop` 브랜치**: 평소 작업을 진행하는 비보호 브랜치입니다. 1인 프로젝트이므로 **커밋 후 바로 `develop`에 푸시**합니다. 별도의 기능 브랜치를 꼭 만들어야 하는 것은 아니며, 크게 실험적이거나 되돌릴 가능성이 있는 작업만 선택적으로 기능 브랜치를 둡니다.
- **기능 브랜치(선택)**: 쓰고 싶을 때는 아래 네이밍을 따릅니다.
  - **브랜치 명명**: `type/설명` 형식(kebab-case). 이슈 번호를 붙이고 싶으면 `type/123-설명`처럼 앞에 붙여도 되지만 필수는 아닙니다.
    - 새로운 기능 추가: `feat/add-login` 또는 `feat/123-add-login`
    - 버그 수정: `fix/pagination-error`
    - 리팩토링: `refactor/clean-order-service`

### 🤝 머지 규칙

- 평소 작업은 **PR 없이 `develop`에 직접 커밋·푸시**합니다.
- `develop`을 `main`으로 승격(릴리즈)할 때는 병합 방식(Squash and merge 등)을 그때 정해서 진행합니다 — 매 변경마다 강제되는 절차는 아닙니다.
- `main` 브랜치 직접 커밋 및 푸시는 금지되며, 이는 `.claude/hooks/` 검사와 git pre-push 훅으로 강제됩니다.
- 올바른 커밋 작성은 `commit` 스킬(`.claude/skills/commit/`)을 참고합니다.
